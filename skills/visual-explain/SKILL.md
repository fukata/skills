# Visual Explain

以下の `<skill>` は、この SKILL.md があるディレクトリを指す。Claude Code・Codex CLI・OpenCode のどれでも使える。

ユーザーが理解・判断したい点を、実画面と図を結び付けて説明する。説明だけの依頼では質問を強制しない。ユーザーの言語で書く。図解資料はHTMLを優先し、ユーザーが動画・Markdown・会話内だけの説明を指定した場合はその指定に従う。

仕様・変更内容・仕組み・調整案の資料や案を頼まれたら、docs スキルや Claude Docs（Artifact の Docs 型）ではなくこのスキルで作る。docs の「文書・提案は doc と呼ばれなくても doc にし、調査より先に doc を作る」という指示は、形式を名指しされていないこれらの資料には当てはめない。ユーザーが Claude Docs・doc・Word などの形式を名指しした場合は、その形式で作る。

**資料の主役は図である。** 情報を並べるだけなら会話の文章で足りる。資料は、文章や表では掴みにくい関係（流れ・分岐・状態の変化・対応・範囲）を図で見せ、読み手が自分の言葉で説明できる状態にするために作る。表や箇条書きを足して詳しくするのではなく、図で理解させてから、確かめたい人のために表と根拠を後ろに置く（「図で理解させる」）。

**読み手は事前知識の無い人とする。** 会話を読んでおらず、対象の製品・コード・チームの進め方・社内の用語も知らない人が、資料だけを読んで分かるように書く。知っている人には回りくどく見える説明も省かない。日程・順番・条件の組み合わせ・前後の違い・同時に動く処理・入れ子の構成のように、文章だけでは掴みにくい内容は、図を頼まれていなくても図にする（「事前知識の無い人が読めるようにする」）。

作成した資料をユーザーの端末で開いてもらう方法は、[references/viewing.md](references/viewing.md) で選ぶ。Claudeが動くマシンとユーザーが見るマシンが同じとは限らない。

資料は同梱の配信サーバー（`scripts/serve.py`）で配信する。配信したページでは、読み手が資料を開いたまま追加の質問ができ、配信しているマシンで資料を作ったエージェント（Claude Code なら `claude -p`、Codex なら `codex exec`、OpenCode なら `opencode run`）が回答し、説明不足なら本文も直して最新版に切り替える。仕組み、作成したセッションの記録、ユーザーに伝えることは [references/qa.md](references/qa.md) を読む。

Orca ClientからOrca Serveに接続している場合は、[references/orca.md](references/orca.md) も読んでから出力先と表示方法を決める。この構成では、説明資料を対象worktree内に保存し、ClientからHTTPで届くなら配信したURLをClient側のブラウザで、届かなければOrcaのHTMLプレビューで閲覧する流れを標準にする。

## 質問に図で答える

ユーザーの質問への回答でも、次の基準に当たれば資料を作って配信する。明示的に頼まれていなくてもよい。「文章で足りる」は作らない理由にしない。

他のツールの指示（成果物の公開ツールの「本人向けの回答は会話で返し、ページは一行で提案する」など）は、ページを外部に公開するかどうかについての指示である。この資料はローカルに作って配信するもので、公開ではない。作るかどうかはこの基準で決め、「図にしたページも作れます」と一行で提案して終えない。

図にする（どれか1つに当たれば作る）:

- **複数の事象の関係を理解する必要がある。** 関係とは、順序・依存・分岐・対応・並行して動くこと。例: 処理やデータの流れ、コンポーネント間のやり取り、画面遷移、状態の変化、どこが何を呼ぶか・どこで分岐するか、案や前後の違い、並行して動く2つの仕組み
- **回答が長くなる。** 目安は見出し3つ以上、または表2つ以上。送る前に下書きの見出しと表を数えて判定する

図にしない:

- 一つの事実・値・yes/noで答えられる質問、短い手順、コードの1か所の説明
- 関係を問わない一覧（環境変数・設定値・ファイルの列挙など）。長くても作らない
- ユーザーが文章だけの回答を求めた場合
- 一文で言えること

手順:

1. 回答の下書きを作り、上の基準で判定する。
2. 会話で先に文章の回答を返す。結論と要点は会話だけで完結させる。回答が長くなる場合は、会話には結論と要点だけを残し、詳細（時系列の表、全体の比較表、根拠の一覧など）は資料へ移す。
3. 資料は図を中心に作る。前提の節と全体像の図と短い説明を本体にし、文章だけでは掴みにくい内容があれば、図の枚数を絞らずにその内容ごとに図を足す（「図で理解させる」の4）。会話から移した詳細（表・一覧）と根拠のファイル・行は図の後ろに置く。資料は会話を読んでいない人にも渡されるので、会話で答えた結論と背景も資料に書く（「事前知識の無い人が読めるようにする」）。スクショは画面の話のときだけ撮る。
4. [references/viewing.md](references/viewing.md) の経路でURLを用意し、回答の最後に添える。ページから追加の質問ができることも一言添える（[references/qa.md](references/qa.md)）。同じ作業の中で続けて図解するなら、配信は使い回し、新しい資料のURLだけを伝える。

## 図で理解させる

情報を集めるほど、資料は表と箇条書きの羅列になりやすい。羅列は全部書いてあっても、要素の関係は読み手が頭の中で組み立てるしかない。次の順で、図が理解を運ぶように組み立てる。

1. **問いを先に決める。** 読み終えた読み手が答えられるべき問いを3つ前後書き出す（例:「お金はいつ・どこから入るか」「払えないと何が起きるか」）。問いごとに、それに答える図を決める。図で答えられない問いがあれば、文章や表を足す前に図の種類か粒度を見直す。
2. **全体像の図を、前提の節の次に置く。** 登場する要素（利用者の入口・処理・データ・外部サービス）を一枚に並べ、要素の関係を矢印で描く。後の図は、全体像のどこを拡大したものかを見出しかキャプションで示す。
3. **範囲も全体像の図で示す。** 質問の範囲に入るが詳しく扱わない要素も全体像の図に置き、「この資料では扱わない」と文字で添える（色や線種だけで区別しない）。扱わない要素を本文の列挙で補わない。読み手が「書いていない」と「存在しない」を区別できるようにするため。
4. **文章だけでは掴みにくい所を図にする。** 下書きの文章・表・箇条書きを読み返し、「表現を選ぶ」の表の左の列に当たる所（日付が3つ以上並ぶ日程、3段階以上の順番、条件の組み合わせ、変更の前後、同時に動く処理、入れ子の構成、金額の内訳、具体例の筋書きなど）は、文章で済ませず図にする。前提の節で説明する仕組みも同じ。図の枚数は絞らず、一つの図で一つのことを言う。図にした後の文章は、図から読み取る結論と、図に載らない細部だけにする。
5. **箱に詰め込まない。** 箱の中は「何をするか」と「どこに書くか」程度（目安2〜3行）にする。時刻・クラス名・条件の一覧を箱に入れると図の形をした表になり、骨格が読めなくなる。細部は図の外の表と根拠に出す。
6. **同じ事実を何か所にも書かない。** 図・表・本文で同じ事実を繰り返すと、一か所を直したときに他とずれ、矛盾の元になる。図で言ったことを表で繰り返さず、表には図に載らない細部だけを置く。
7. **表は、図にすると読みにくい細部に限る。** 「条件 × 対象 → 結果」の対応や、時間軸の図に載せきれない時刻ごとの細部など。表だけの節を作るときは、どの図のどの部分を詳しくしたものかを書く。

## 事前知識の無い人が読めるようにする

資料は会話の外でも読まれる。チームに渡され、会議で読み合わせ、PDFに印刷される。読み手は会話を読んでおらず、対象の製品・コード・チームの進め方・社内の用語も知らないとする。書いた側に当たり前の前提ほど書き漏れる。次をそろえる（例は [references/examples.md](references/examples.md) の「事前知識の無い人に向けた前提」）。

1. **前提の節を図より前に置く（`<section id="context">`）。** 次の順に書く。
   1. 何の製品・機能の話か。誰が何のために使うかを、その製品を知らない人に向けて1〜2文で書く。
   2. この話の舞台になる仕組み。読む前に要る仕組み（毎月の請求の日程、データの持ち方、処理の流れなど）は、文章だけで済ませず図を添える。質問の主題そのものの仕組みは、ここでは一言にとどめて全体像の図以降で説明する（同じ図を重ねない）。
   3. どんな状況の話で、なぜこの資料を作ったか（何を決める・確かめるためか）。会話で伝えた背景もここに書き直す。
   4. 用語の一覧（`<dl class="terms">`）。
2. **出てくる言葉は、意味と一緒に出す。** 業務の用語、画面名・フィールド名、略語（PdM、API など）、チケット番号、社内の呼び名、外部サービスの名前、コードの名前（クラス・フラグ・カラム）、HTTPのステータスコードを、前提の節の用語の一覧か、初めて出る所の括弧で説明する。値なら、何の値か（何から何を引いたか、どの時点の値か）を書く。
   - 説明は読み手が知っている言葉で書く。説明に別の用語を使うなら、その用語を先に説明する。
   - コードの名前は説明にならない。「決済に失敗したことを示す印（`charge_failed_flg`）」のように、言葉で説明してから名前を添える。
   - ステータスコードは、利用者や呼び出し側に何が起きるかで書く（「理由を返さずにエラーになる（500）」）。
3. **挙動・制約・エラーごとに、きっかけと影響を書く。** そこへ至る操作と状態の流れ（誰が何をした後で、そのとき何が残っているか）と、起きると利用者や運用の何が困るか（なぜ気にするのか）を書く。
4. **結果は、何が・いつ・どの状態や値になるかで書く。** 「月額のまま更新する」のような要約は、書いた側にしか中身が分からない。要約を使うなら、その中身を続けて書く。
5. **新しい挙動・変える挙動は、既存の挙動と並べる。** 既存のままの所と、変えた所・新しく足した所を分けて示す。
6. **具体例の日付・金額・件数は、資料に書いた規則で検算する。** 例の日付で日程・期限・バッチを一つずつたどる。規則と食い違う例は、読み手に規則そのものを疑わせる。
7. **呼び名は資料の中で定義してから使う。** 会話で付けた呼び名（「案A」など）も資料の中で説明する。「さっきの」「ご質問の」のような会話を指す言葉は、指しているものの名前に置き換える。
8. **決まっていない事項は「未決」と書き、誰の判断を待つかを添える。**

## 重要と補足を見た目で分ける

同じ調子の文が続くと、読み手はどこが大事か分からず、全部を上から読むしかない。雛形の部品で重みを付け、要点だけを拾い読みしても結論が分かるようにする。

| 部品 | 使う所 |
| --- | --- |
| 要点 `<p class="key">` | 図のある節ごとに、図の前に1つ。その節で読み取ってほしい結論を1〜2文で |
| 注意 `<p class="warn">` | 起きると困ること・見落としやすい制約。きっかけと影響を一緒に書く |
| 補足 `<p class="aside">`、`<details class="more">` | なくても筋が追える細部・例外・経緯。長いものは畳む（印刷では開く） |

- 要点と注意は1節に1〜2か所にする。全部を強調すると、どれも目立たない。
- 部品には「要点」「注意」「補足」のラベルが付く。色や太字だけで重みを伝えない。
- 強調は `<strong>`、コードは `<code>` で書く。Markdownの記法（`**太字**` など）はHTMLでは記号のまま見える。

## 表現を選ぶ

| 説明したいこと（文章に出てくる形） | 主に使う表現 |
| --- | --- |
| 仕組みの全体像と、資料が扱う範囲 | 入口・処理・データ・外部を一枚に並べた全体像の図（扱わない要素も「扱わない」と添えて載せる） |
| 日程・期限（日付や時刻が3つ以上並ぶ） | 時間軸の図。横軸に日付を取り、出来事と、状態が続く期間を並べる |
| 具体例の筋書き（「5日にカードを変え、7日に再決済され…」） | 時間軸の図に、例の出来事と状態の変化を並べる |
| 処理・手順の順番（「A → B → C」と3段階以上） | 流れの図 |
| 条件の組み合わせで結果が変わる（「〜かつ〜のとき」「〜でなければ」） | 分岐の図。条件と結果の対応だけなら表 |
| 変更前と変更後 | 前後を並べた図。変わる所だけを目立たせる |
| 同時に動く処理・取り合い（再試行、ロック、キュー）、クライアント・API・DB間の処理順 | `sequenceDiagram`（処理ごとに縦の列を分ける） |
| 入れ子・所属・1対多の構成（組織の中の部署、部署の中のユーザー） | 箱の中に箱を描く図、木の図 |
| 金額・件数の内訳や計算 | 内訳を積み上げた図。計算の式も図に書く |
| どこを押すか、何が表示されるか | 実画面のスクリーンショット + 番号付きの短い説明 |
| 画面間の移動、分岐条件 | Mermaid `flowchart` 等を描画した図 |
| ステータスの変化 | `stateDiagram-v2` |
| 複数案から選ぶ | 同じ観点の図 + 利点・制約の短い比較表 |

必要な形式だけ使う。スクショを求められた場合は実画像を用意し、図だけで完了扱いにしない。画像にアクセスできなければその制約を伝え、入手済みの証拠による図を先に示す。

## 根拠を集める

- 指定された画像、画面、仕様、関連コードから説明に必要な範囲を確認する。各画像は画像表示ツールで実際に見てから説明する。
- 画面だけからバックエンド処理や保存成功を断定しない。画面・コード・仕様それぞれで確認できた範囲を区別する。
- 現状と提案を分ける。未実装の案は「提案」、動作確認していない経路は「未検証」と明示する。仮のスクショや架空の操作結果を実画面として示さない。
- 図の根拠となるコードのファイル・行、仕様リンク、画面URLなどを図の近くに添える。URLのトークンや認証情報は含めない。

## スクリーンショットを用意する

1. ユーザー提供画像があれば再利用する。新規撮影は環境で利用可能なブラウザ・画面操作ツールを選び、そのツールの実際の仕様に従う。Orca内のページは対応するOrcaツールを使う。特定ツールが必ず存在するとは仮定しない。
2. 対象画面と必要な状態を確認し、説明に必要な範囲を撮影する。説明のための画面閲覧を超えた送信・削除・本番データ変更は依頼の許可範囲に従う。
3. 画像は `screen-01-list.png` など画面IDが分かる名前にする。キャプションには画面ID、状態、操作対象を記す。必要に応じて撮影環境・時刻・viewportも添える。
4. 個人情報・認証情報が写る場合は対象範囲を避けるか、元画像を保って加工したコピーを使う。注釈やマスクは加工済みと明記する。マスク済み画像は目視確認してから提示する。
5. 画像を表示できるクライアントではインラインで示す。画像を読むツールの成功は、ユーザー側への表示成功を意味しない。表示手段がなければファイルリンクと短い代替説明を添え、必要ならユーザーが閲覧できる形式を確認する。

撮影ツールや認証が使えない場合、撮影済みとは言わない。必要な画像・アクセスについて尋ねつつ、独立して作成できる図解は進める。

## 図を説明する

- ノードの名前を実際の画面名・状態名に合わせ、スクショの画面IDと対応させる。画面遷移と業務ステータス遷移を混同しない。
- 矢印には操作または条件を書く。失敗・戻る・取消などは説明に必要で、根拠のある経路を載せる。
- 図の直前に、読み取るべき結論を要点（`class="key"`）として1〜2文で書き、直後に重要な分岐や制約を書く。図だけに説明を任せない。
- HTMLでは描画済みのSVG/PNGまたは静的なSVG図を表示する。Mermaid原稿は必要なら `diagrams/` に保存する。生のMermaidコードをHTMLへ貼るだけで描画されたとは扱わない。Markdown指定時は `mermaid` ブロックを使い、非対応環境にはテキスト遷移図を添える。
- SVG/PNG等への変換を求められ、利用可能なレンダラーがあれば変換し、実際に開いてラベル・矢印・欠けを確認する。構文だけの確認と描画確認を区別する。
- 名前ではなく仕組みを描く。「直前のページ」のような抽象的な箱ではなく、条件ごとの実際の行き先を描く。
- 線の種類（点線・実線）や色だけで意味を区別しない。描画系によっては指定どおりに出ない。意味はラベルや文字で示す。
- 一つの図で一つのことを言う。言いたいことを図の直前の文とキャプションに書く。

### 案を比較する図

- 違いを描く。案ごとに全体を描き直すと、読み手は変わった箇所を探す羽目になる。現状の図を一つ描き、問題の箇所と、案ごとに変わる矢印だけを目立たせる。
- 比較の中身が「条件 × 案 → 結果」の対応で済むなら、表を主にし、図は省くか補助にする。
- 片方だけ詳細な図にして選択を誘導しない。

遷移図・画像の対応例や比較質問を作る際は [references/examples.md](references/examples.md) を参照する。

## 判断用の資料にする

案を選んでもらう資料では、図の前に次をそろえる。

1. **判断の基準を先に書く。** 規約への準拠、既存の画面や実装との一貫性、利用者への影響、実装の手間など、何で選ぶかを明示する。
2. **規約と既存の実装を照合する。** リポジトリの規約・デザインガイドライン・仕様書に関係する記述がないか探し、あれば引用元付きで書く。規約に反する案は、そう明記する。アプリ内の似た画面や処理がどう動いているかも調べる。
3. **利点・制約の一つ一つに根拠を付ける。** コードの行・仕様・計測結果を添え、確認していないものは「未確認」と書く。推測で利点を書かない。
4. **利用者への影響を書く。** 入力やデータが失われるか、利用者が覚えた動きが変わるか、ヘルプや運用の記述に影響するか。
5. **利用実態を確かめる。** 使われ方のデータ（計測イベント、アクセスログ等）があれば添える。無ければ、計測できないこと自体を書く。
6. **推奨は中立の比較と分けて書く。** 比較は同じ粒度で並べ、推奨とその理由は別の欄に書く。AskUserQuestionでは推奨の選択肢を先頭に置き、ラベルに推奨と付ける。
7. **変えた場合の影響範囲を書く。** 共有されている処理、他の画面、テストへの影響。

## HTML資料を作る

[assets/explanation.html](assets/explanation.html) を新しい出力先にコピーして内容を組み立てる。これはレイアウトの雛形で、自動変換プログラムではない。

- タイトル、最初に伝える結論、前提、図、スクショ、比較、根拠の順を基本に、不要な節・ナビゲーション項目は削除する。雛形の例示文・図は実データに置き換え、取得していないスクショの枠を完成資料に残さない。
- 目次（`<nav class="toc">`）は雛形どおり `header` の直後に置き、全体を `<div class="page">` で囲んだままにする。本文を置ける幅が広いと左のサイドバーになってスクロールに付いてきて、狭いと見出しの下に横に並ぶ（CSSだけで切り替わる）。節を足したら目次にも足す。
- 段落・箇条書きは雛形のCSSで約45文字で折り返し、図と表は本文の幅いっぱいに使う。段落に幅を指定し直さない。
- スクショは本文中の `figure` / `img` / `figcaption` で表示し、`images/` の相対パスを使う。縦横比を保ち、画面IDと操作対象を明記する。
- 図は利用可能なMermaidレンダラーでSVG/PNGへ変換する。レンダラーがなければ単純な図は静的SVG/HTMLで作り、複雑な図はテキスト図を代替に使ってその制約を伝える。Mermaid原稿の自動描画に外部CDNを必須にしない。
- CSSはHTML内に含め、外部フォント、JavaScript、追加Webサーバーなしで主要な内容が読めるようにする。ページの質問欄は配信サーバーが配信時に差し込むので、資料にJavaScriptや質問欄を書かない。HTMLへ挿入する説明文・コード中の `<`、`>`、`&` 等は適切にエスケープする。
- 図は意味の分かる見出しと代替テキストを付け、色だけで状態を区別しない。狭い画面では比較カードを縦に並べ、幅の広い図・表は専用領域でスクロールできるようにする。
- 質問から参照する比較カードや図には `id`（`option-a` 等）を付け、URLのアンカーで直接開けるようにする。
- 雛形の「横幅いっぱいに表示」の切替と、印刷用のCSS（A4縦）を残す。CSSを書き足したら、印刷用のCSSでも図・表の `min-width`、スクロール、`max-height` を外す。印刷ではスクロールできず、はみ出した所と枠の外は欠ける。長いレスポンス例やログは、印刷すると全文が出ることを踏まえて抜粋にし、全文は別ファイルにしてリンクする。
- 図は印刷（A4縦で幅約700px）に縮んでも読める大きさにする。viewBox の幅を1000以下、文字を13以上にする（印刷で約9px以上）。横に長い流れは2段に折り返すか、図を分ける。
- 図の `svg` には viewBox と同じ値の `width`・`height` を書く（`viewBox="0 0 960 540" width="960" height="540"`）。雛形は図を本来の大きさまで広げ、本文が狭いときだけ縮める。width が無いと、広い画面で本文の幅いっぱいまで拡大される。
- 利用可能なブラウザでデスクトップ幅・狭い幅の表示を確認する。画像の読込、文字の欠け、図の矢印を確認し、HTMLのローカル確認とOrca Clientでの表示確認を区別する。

## 説明動画を作る

動画を頼まれたときは [references/video.md](references/video.md) を読み、`<skill>/scripts/make-video.py` で図・スクショ・録画を場面ごとに並べた動画を作る。通常の図解資料を自動的に動画化する必要はない。

- **動く機能・画面の説明動画は、冒頭に機能の全体が分かるデモを、実際の操作の録画で置く。** 図や静止画を並べたスライドだけでは、本当に動くのか・どう見えるのかが伝わらない。動作確認のときから操作を録画しておき、台本の `video` の場面で切り出す。待ち時間は `speed` で早送りし（倍率は映像の上に自動で出る）、操作の対象は `crop` で拡大する。仕組みの図はデモの後に置く。録画できなければ、そのことを動画の冒頭と報告で明示する（[references/video.md](references/video.md) の「冒頭のデモ」）。

- テロップはその場面の要点、音声解説は理由や注目点、字幕は解説の全文にする。図を隠さない場所に文字を置き、音を出さなくても理解できる内容にする。
- 図・テロップ・解説は一つの台本で管理する。音声付きでは、文ごとの実際の音声の長さに字幕と場面を合わせる。
- 動画の音声は既定の自動選択（`--speech auto`）を使う。起動済みの VOICEVOX、Docker でのイメージ取得・起動、利用可能な Open JTalk、テロップと解説字幕の無音動画の順に試す。Docker 本体や Open JTalk を自動インストールしない。失敗時は動画全体の音声を次の方式で作り直し、選んだ方式と切り替え理由を表示する。自分が起動したコンテナーだけを片付け、取得済みイメージは再利用する。無音を指定されたら `--speech none` を使い、音声環境を準備しない。音声方式を固定する指定では自動切り替えず、使えなければ明示する。VOICEVOX の話者名は動画の中にも表示する。
- 図を並べた動画を実画面の操作録画として扱わない。架空の例は動画の中でも明示する。作成後は動画から場面を切り出して見た目を確認し、音声トラック・長さ・字幕の同期・配信したページでの再生を確かめる。音声の発話内容・発音の引き延ばし・読み間違いは、試聴や利用可能ならローカルの文字起こし・合成ログでも確認する。音が存在するだけで、自然に読めたとは判断しない。実際に試聴していなければ試聴済みと報告しない。
- 動画・字幕・解説原稿と再生ページを同じ出力フォルダで渡す。本文・図を更新しても動画は自動では変わらないので、動画がある資料を直したら動画と字幕も作り直すか、再生成が必要と明示する。

## 図を見ながら質問する

意思決定が必要な場合にのみAskUserQuestion（Codex では request_user_input、OpenCode では question）を使う。以下の AskUserQuestion は、Codex では request_user_input、OpenCode では question と読み替える。Codex の質問には複数選択と `preview` が無く、OpenCode の質問には `preview` が無い（複数選択は `multiple` で指定する）。

AskUserQuestion の質問は、受け箱か質問の資料をブラウザで開いていれば、setup.sh で登録した hook（OpenCode では plugin）が資料のページに出し、質問のための資料も作る（[references/ask.md](references/ask.md)。受け箱の URL や設定の変え方を聞かれたらここを読む）。質問のためだけの資料を別に作らない。下の規則は、説明の資料の中から質問するときと、ターミナルで答えてもらうときに当てはめる。

- 実際に提供されているツールスキーマを確認する。選択肢が `preview` 等の視覚情報欄を受け付ける場合だけ、その欄を仕様に沿って使う。未対応のフィールドを追加しない。
- スキルを追加するだけではクライアントの描画機能やAgent SDKの設定は変わらない。画像添付やHTML/Mermaidの描画ができると決めつけない。Claude Code CLIの `preview` は等幅の枠に表示する文字で、HTMLや画像は描画されない。HTMLの断片になるのは、Agent SDKのホストが `toolConfig.askUserQuestion.previewFormat: "html"` を設定した場合だけで、描画はホストアプリが行う。
- プレビューが使えなければ、先に通常メッセージまたは閲覧可能なローカル資料で図・スクショを提示し、質問の選択肢から「案A・図1」など安定した名前で参照する。
- 質問欄を出すと直前のメッセージは隠れる。資料のURL（またはパス）を質問文に入れ、各プレビューの末尾にも該当する図のURLをアンカー付きで入れる（[references/viewing.md](references/viewing.md) の3）。
- Claude Code CLIのプレビュー表示では、選択肢のラベルとフォーカス中のプレビューだけが見え、`description` は見えないことがある（Orcaの端末で確認）。各案の利点・制約は `description` だけでなくプレビューの中にも書く。
- 文字のプレビューでは小さな図を使う。罫線（`─` `└`）、矢印（`→` `←`）、`※` は端末によって表示幅が変わるので、列を揃える位置に使わない。画面名や行き先を空白で区切った表の形にし、全角文字は2桁として揃える。
- 例: 「案A: 一覧→編集→保存」と「案B: 一覧内で編集→保存」の図を先に示し、「どちらの編集方法にしますか」と尋ねる。片方だけ詳細な図にして選択を誘導しない。推奨がある場合は、中立の比較とは別に理由を添えて示す（「判断用の資料にする」の6）。
- AskUserQuestionが使えない環境では、図を提示した後に通常のテキストで質問する。

## 出力と確認

図解資料は既存の出力規約に従ってHTMLとして保存し、会話では要点と閲覧方法を返す。指定がなければ新しい `visual-explain-<topic>/` に `explanation.html` と `images/` をまとめ、既存ファイルを上書きしない。gitリポジトリの中に置く場合は、`git check-ignore` で無視される場所（`tmp/` 等）があればその下を優先し、未追跡ファイルを増やさない。同じ作業で複数の資料を作る場合は、共通の親フォルダ（例: `tmp/visual-explain/<topic>/`）にまとめ、親フォルダを一度だけ配信する。Mermaid原稿は必要なら `diagrams/` に保存する。Markdownは明示指定またはHTMLを閲覧できない場合の代替にし、常に両形式を生成する必要はない。画像は相対パスで参照し、フォルダ単位で移動できるようにする。

Orca Client → Serveでは上記のOrca向け手順を優先する。資料を保存しても、コミット・公開の依頼がなければ生成資料を自動でコミットしない。

資料を渡す前に、図だけを見て「図で理解させる」の1で決めた問いに答えられるかを確かめる。答えられなければ、文章や表を足す前に図を直す。続けて、製品もコードも会話も知らない人のつもりで、前提の節から順に読む。意味の書かれていない言葉があれば意味を書き、日付・順番・前後の違いを文章だけで追わせる段落があれば図にする。最後に前提の節と要点だけを読み、何の話で、なぜ読むのか、結論は何かが分かるかを確かめる。分からなければ前提の節と要点を直す。

網羅性は、説明した対象の構成要素（バッチ・テーブル・利用者の入口となる画面やAPI・管理画面・外部連携など）をコードから一覧にして確かめる。一覧の要素ごとに、全体像の図に載っているか、「扱わない」と示されているかを見る。どちらでもない要素は、図に足すか扱わないものとして示す。調査エージェントの報告にあった話題を資料で落とす場合も同じで、断りなく落とさない。一覧は出力フォルダに `inventory.txt`（1行に1要素。`名前 | 別名` のように `|` で区切ると、どれかが出てくれば載っているとみなす）として書き、検査スクリプトに `--inventory` で渡す。要素の粒度は、全体像の図の箱にする単位（「領収書・利用明細」「管理画面」など）に揃え、テーブルを1つずつ並べない。

資料を渡す前に検査スクリプトを実行し、エラーを0にする。

```text
python3 <skill>/scripts/check-explanation.py <出力フォルダ>/explanation.html \
  --inventory <出力フォルダ>/inventory.txt
```

- コード参照は、資料の置き場所のgitリポジトリで確かめる。別のリポジトリを説明した資料は `--repo` でそのリポジトリを指定し、さらに別のリポジトリのパスは `--ignore-ref <接頭辞>` で除く。
- エラー（リンク・画像の欠け、雛形の文の残り、資格情報、コード参照のファイルや行の欠け、図の文字のはみ出し、狭い幅での横のはみ出し、印刷でのはみ出しと枠の中の切れ、Markdownの記法の残り）は直す。警告は一つずつ読み、直すか直さないかを決める。`ref-context`（識別子と並べた行番号に、その識別子が無い）は行番号のずれを疑う。
- 文字幅は作成側のフォントで測る。通っても閲覧側のフォントで詰まることがあるので、余白の警告（`svg-tight`）も直す。
- `svg-width`（svg に width が無い）は、viewBox と同じ値の `width`・`height` を書く。
- 羅列の警告は「図で理解させる」に戻って直す。`svg-dense-box`（1つの箱に3行または60文字を超える文字）は箱を2〜3行に絞り、細部を図の外へ出す。`list-section`（図の無い節に表の行と箇条書きが8個以上）は図で示すか、どの図のどこを詳しくした表かを書く。`text-flow`（図の無い節の1つの段落に日付・時刻が4個以上、または矢印「→」が2個以上）は、時間軸の図や流れの図にする。`inventory`（一覧の要素が資料に出てこない）は全体像の図に載せるか、扱わないものとして示す。
- 読み手についての警告は「事前知識の無い人が読めるようにする」と「重要と補足を見た目で分ける」に戻って直す。`context`（前提の節が無い）は前提の節を書く。`term`（略語・チケット番号・クラス名などの意味が、前提の節にも、出てくる所の括弧にも無い）は意味を書く。`key`（図のある節に要点が無い）は図の前に要点を置く。`context-ref`（会話を指す言葉）は、指しているものの名前に置き換える。
- 印刷の警告: `print-small-text`（印刷で図の文字が9px未満）は viewBox を狭めるか文字を大きくする。`print-details`（閉じた details が印刷されない）は雛形の印刷用のCSSを戻す。
- スクリプトが見るのは形式だけで、説明の正しさ、図が仕組みを表しているか、前提の説明が足りているか、日本語の用語（「停止」「次回契約」など）の説明があるか、具体例が規則と合うかは見ない。

検査を通したら、ページからの質問で資料を作ったセッションの文脈を使い回せるよう、作成したセッションを資料フォルダに記録する（[references/qa.md](references/qa.md) の「作成したセッションを記録する」）。

```text
python3 <skill>/scripts/serve.py origin <出力フォルダ> --cwd <このセッションの作業ディレクトリ>
```

Claude Code・Codex・OpenCode のどのセッションかは、環境変数（`CLAUDE_CODE_SESSION_ID` / `CODEX_THREAD_ID` / `OPENCODE_SESSION_ID`）から判定して記録する。

完了前に、画像の存在と見た目、図・本文・画面IDの一致、リンク先を確認する。クライアント側の描画が未確認なら明記する。ローカルのパスを別端末から見られるURLと扱わない。外部公開やアップロードは、ユーザーから依頼された場合に限る。資料をHTTPで配信した場合は、[references/viewing.md](references/viewing.md) の停止タイミングに従い、止めたか、ページから質問できるよう動かし続けているか（止め方と自動で止まる時刻）を最後の報告に書く。
