# 資料を見せる経路

作成した `explanation.html` を、ユーザーが使っている端末のブラウザで開いてもらうための手順。エージェント（Claude Code・Codex）が動くマシン（以下「作成側」）とユーザーが画面を見るマシン（以下「閲覧側」）が同じとは限らない。

## 1. 経路を選ぶ

上から順に、使える最初の経路を選ぶ。

| 閲覧側の状況 | 経路 | ユーザーに案内するもの |
| --- | --- | --- |
| 作成側と同じマシン（WSL・devcontainerの中で動いている場合を含む） | HTTP配信（`127.0.0.1` で待ち受け） | `http://localhost:<port>/explanation.html?k=<合言葉>` と、代替のファイルのパス |
| 作成側と同じマシンで、Python 3が無い | ファイルを直接開く（ページからの質問は使えない） | `file:///<絶対パス>/explanation.html`（WSLでは `wslpath -w <絶対パス>` で変換したWindows側のパス） |
| 別マシンで、作成側のアドレスへプライベートネットワーク（Tailscale、社内LAN、VPN等）で届く | HTTP配信（そのアドレスだけで待ち受け） | `http://<アドレス>:<port>/explanation.html?k=<合言葉>` |
| 別マシンで、SSHで接続している | HTTP配信（`127.0.0.1` で待ち受け）+ SSHポート転送 | 転送コマンドと `http://localhost:<port>/explanation.html?k=<合言葉>` |
| Orca Client → Serveで、上の経路が使えない | Orcaのファイル接続でプレビュー（ページからの質問は使えない） | [orca.md](orca.md) の経路B |
| どれも使えない | フォルダごと転送してもらう、またはMarkdownで代替 | フォルダの場所と転送方法 |

同じマシンでもHTTP配信を既定にするのは、ファイルのパスがブラウザで開けないことが多いため。もう一つの理由は、同梱の配信サーバーで配信したページでは追加の質問ができるため（[qa.md](qa.md)）。

- WSLで動いている場合、`/home/...` のパスはWindows側のブラウザで開けない。WSL2はWindowsの `localhost` へポートを転送するので、`127.0.0.1` で待ち受ければ届く。
- devcontainerで動いている場合、コンテナ内のパスはホストのブラウザで開けない。VS Codeは待ち受けたポートを自動で転送する。
- VS Codeの端末では、ファイルのパスをクリックするとエディタでHTMLのソースが開く。`http://` のURLはブラウザで開く。

判断の材料:

- `SSH_CONNECTION` も `ORCA_` で始まる環境変数も無ければ、同じマシンとして扱う。
- `/proc/version` に `microsoft` を含めばWSL。
- `SSH_CONNECTION` があればSSH経由の接続。3番目の値は、閲覧側から届いた作成側のアドレスである。
- `ORCA_` で始まる環境変数があればOrcaの端末。Client → Serve構成かは [orca.md](orca.md) で確かめる。
- Tailscaleがあれば `tailscale ip -4` で作成側のアドレスが分かる。
- 分からなければ、どの端末で見るかを一度だけ尋ねる。推測でアドレスを公開しない。

同じネットワークでも、社内LANのように他人の端末がいるネットワークでは、HTTP配信より、本人だけが使うSSHポート転送を優先する。グローバルアドレスでは待ち受けない。

## 2. HTTP配信

同じ作業の中で配信中のものがあれば、新しく立てずに使い回す。新しい資料は配信中のフォルダの下に置き、URLだけを伝える（配信中に足した資料にもページの質問欄は出る。合言葉は起動したときのものを使う）。

1. 空いているポートを選ぶ（`ss -ltn`、macOSでは `lsof -iTCP -sTCP:LISTEN` 等で確認）。
2. 出力フォルダ（複数の資料をまとめるなら、資料だけを置く共通の親フォルダ）だけを、選んだアドレスだけで待ち受けて、同梱の配信サーバーで配信する。`0.0.0.0` や全インターフェースでは待ち受けない（配信サーバーも起動を断る）。上限時間（既定2時間、`--max-time` で変更）で自動で止まる。バックグラウンドで起動する。

   ```text
   python3 <skill>/scripts/serve.py serve --dir <出力フォルダ> --port <port> --bind <アドレス> --repo <説明したリポジトリ>
   ```

   `--repo` は、ページからの質問に新しいセッションで答えるときの作業ディレクトリと、本文を直した後の検査の `--repo` に使う（省略すると出力フォルダのgitリポジトリ）。起動すると、資料ごとの `?k=<合言葉>` 付きのURL、プロセスID、質問を受け付けるかが標準出力に出る。`claude` が無ければ静的配信だけになる。ページからの質問には Web と MCP も使って答える（資料とリポジトリだけで答えさせるなら `--local-only` を付ける）。IPアドレス・`localhost`・このマシンの名前・`*.ts.net` 以外のホスト名（社内DNSの名前など）で開いてもらう場合は、`--allow-host <名前>` を付ける（付けないと403になる）。

3. 作成側から `curl` で `explanation.html` と画像が200になることを確認する。
4. 出力に出た `?k=` 付きのURLを案内する。合言葉の無いURLでも資料は読めるが、質問は送れない（一度 `?k=` 付きで開けば、同じブラウザでは図ごとのアンカー付きURLなど `k` の無いURLでも質問できる）。同じマシンの経路では、開けなかったときの代替としてファイルのパスも併記する。SSHポート転送の経路では、閲覧側で実行するコマンドも示す。

   ```text
   ssh -L <port>:127.0.0.1:<port> <作成側のホスト>
   ```

5. 配信しているフォルダ、アドレス、上限時間を伝える。プライベートネットワークでの配信は、同じネットワークの他の端末からもACL次第で見える（質問を送るには合言葉が要る）。
6. 資料を直したら、同じ配信のまま待ってもらう。開いているページは数秒で最新版に切り替わる。配信の再起動は要らない。
7. 開けないという返答があったら、配信を止めて次の経路に切り替える。

配信を止めるタイミング:

| 状況 | 止めるとき |
| --- | --- |
| 質問がある | 回答を受け取り、資料をもう更新しないと判断したとき |
| 説明だけ | ユーザーが読み終えたと伝えたとき。言われないまま作業を終えるなら、ページから質問できるよう動かしたままにし、上限時間で自動で止まることと止め方（`kill <プロセスID>`）を伝える |
| 質問への回答に図を添えている | 同じ作業で続けて使う間は動かしたままにする。話題が図の要らない作業に移ったら、ページからの質問を待っていないか確かめてから止める。作業を終えるときは「説明だけ」と同じ |
| ページからの質問を処理中 | 止めない。止めると処理中の質問は「中断」になる。配信の標準エラーで処理が終わったことを確かめてから止める |
| 別の経路に切り替える | 切り替える前 |
| 止め忘れ | 上限時間（`--max-time`、既定2時間）で自動的に止まる |

ユーザーが配信を続けるよう求めた場合は止めない。止めたこと、または動かし続けていることと止め方を、最後の報告に書く。バックグラウンドで起動した配信は、Claude Code のセッションを閉じると一緒に止まることがある。

## 3. 質問から資料へ戻れるようにする

AskUserQuestionを出すと、直前のメッセージは質問欄に隠れる。資料のURL（経路によってはパス）を質問文に入れ、各選択肢のプレビューの末尾にも、該当する図のURLをアンカー付き（`#option-a` 等）で入れる。Claude Code CLIでは、質問文とプレビュー内のURLをクリックできた（Orcaの端末で確認）。

## 4. 確認の段階を分けて報告する

1. **作成確認**: 資料と画像があり、参照先が実在する。
2. **表示要求**: URLやパスを案内した、または開く操作が受理された。
3. **閲覧側の表示確認**: ユーザーから図と画像が見えたと回答があった。

作成側での画像閲覧、`curl` の成功、CLIの成功だけで3を満たしたと報告しない。確認できなければ「閲覧側の表示は未確認」と短く記す。
